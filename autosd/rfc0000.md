# RFC NNNN - Standalone Supervisor Mode for Automotive QM Environments

## Summary

Add a `--standalone` flag to the OpenShell supervisor that disables all gateway-dependent features, enabling fully self-contained operation with static file-based configuration. This mode is designed for resource-constrained, air-gapped environments like automotive Quality Management (QM) systems where dynamic policy updates and telemetry submission are prohibited by certification requirements.

Standalone mode requires boot-time policy configuration from local files, eliminates polling loops and background aggregators, disables SSH server and supervisor session, and provides deterministic startup/shutdown with minimal resource footprint. Standalone sandboxes can be deployed using systemd/Podman Quadlets for declarative, boot-time service management.

## Motivation

### Automotive QM Requirements

Automotive Quality Management environments have constraints that make gateway-integrated deployment unsuitable:

1. **Air-gapped operation** - Control plane connectivity is prohibited; systems are network-isolated
2. **Static certification** - Dynamic policy updates violate certification requirements; policy must be validated at build time
3. **Severe resource constraints** - Embedded systems with limited CPU/memory/storage
4. **Deterministic behavior** - No retry loops, no polling, predictable startup/shutdown mandatory
5. **Boot-time availability** - All components must be operational at system boot without external dependencies
6. **Agent autonomy** - AI agents run as the entrypoint process; no interactive shell required
7. **systemd integration** - Services managed by systemd for lifecycle, dependencies, and restarts

### Current Limitations

The supervisor already supports file-based policy via `--policy-rules` and `--policy-data` flags, but even with these set, the supervisor:

- Attempts gateway connection if `--openshell-endpoint` is set
- Runs polling loops (settings poll every 10s) even when policy is file-based
- Spawns aggregators that try to flush to unavailable gateway
- Runs SSH server for relay access (unnecessary in air-gapped environment)
- Fills logs with "Failed to flush to gateway" warnings
- Wastes resources on background tasks providing no value

### Target Use Cases

Beyond automotive QM, standalone mode serves:

- **Edge and embedded deployments** - Gateway connectivity unreliable or unavailable
- **Compliance-driven environments** - Immutable, verifiable policy required
- **Air-gapped systems** - No external connectivity permitted
- **Resource-constrained platforms** - Minimal footprint critical
- **systemd-managed fleets** - Declarative service definitions, dependency ordering, restart policies

## Non-goals

- **Replacing gateway-integrated deployments** - Cloud/K8s deployments continue using full gateway integration
- **Dynamic policy updates in standalone mode** - Static, boot-time configuration is the design goal
- **Alternative telemetry backends** - Standalone writes local OCSF logs; use platform log forwarding if needed
- **Standalone SSH alternative** - Remote access is platform concern (exec into container, VM console)
- **Supporting provider credentials resolution** - Credentials via environment variables or platform secrets
- **Changing privilege model** - Still requires CAP_NET_ADMIN; runs rootful
- **Separate standalone binary** - Runtime flag, not separate build
- **Agent-driven policy proposals** - RFC 0002 policy advisor workflow is incompatible with standalone mode by design
- **Building a systemd service generator** - Users write their own `.container` quadlet files or systemd units

## Proposal

### New `--standalone` Flag

Add top-level boolean flag that explicitly disables gateway-dependent features:

```rust
#[arg(long)]
standalone: bool,
```

### Behavior Changes in Standalone Mode

When `--standalone` is true:

**1. Validate configuration at startup**
- Error if `--openshell-endpoint` is set
- Error if `--sandbox-id` is set (requires gateway)
- Error if `--policy-rules` is not set
- Error if `--policy-data` is not set
- Error if policy files don't exist or fail validation

| Flag combination | Error message |
|------------------|---------------|
| `--standalone` + `--openshell-endpoint` | "Standalone mode cannot connect to gateway; remove --openshell-endpoint" |
| `--standalone` + `--sandbox-id` | "Standalone mode does not support --sandbox-id" |
| `--standalone` without `--policy-rules` | "Standalone mode requires --policy-rules for static policy" |
| `--standalone` without `--policy-data` | "Standalone mode requires --policy-data for static policy" |

**2. Disable gateway-dependent features**
- Skip supervisor session creation (no gRPC connection to gateway)
- Skip SSH server spawn (no relay access)
- Skip denial aggregator spawn (no flush task)
- Skip activity aggregator spawn (no flush task)
- Skip settings poll loop (no dynamic updates)
- Skip provider credentials fetch (use env vars only)
- Skip log push task (write local OCSF files only)

**3. Use static file-based policy**
- Load policy from `--policy-rules` (Rego) and `--policy-data` (YAML) once at boot
- No hot-reload (immutable for sandbox lifetime)
- Policy must be valid at startup or supervisor exits with error

**4. Deterministic lifecycle**
- Fast startup: no connection attempts, no retry loops (~1s total)
- Clean shutdown on SIGTERM: no aggregator flush delays (~100ms)
- Exit with structured error on invalid configuration
- Compatible with systemd `Type=notify` for ready signaling (future enhancement)

### Configuration Model

Standalone mode uses two required configuration files:

**Policy Rules** (`--policy-rules`): Rego policy file for OPA engine

**Policy Data** (`--policy-data`): YAML file with SandboxPolicy protobuf message

**Minimal example:**

```yaml
# /etc/openshell/policy-data.yaml (minimal example - see docs for full schema)
network_policies:
  - name: allow-github
    mode: layer4
    endpoints:
      - host: github.com
        port: 443
    binaries:
      - path: /usr/bin/git
    status: approved
process:
  run_as_user: "sandbox"
  run_as_group: "sandbox"
```

### systemd/Podman Quadlet Integration

Standalone sandboxes integrate naturally with systemd-managed container deployments via Podman Quadlets. A quadlet is a declarative `.container` file that systemd-generator converts to a standard `.service` unit at boot.

**Example Quadlet** (`/etc/containers/systemd/openshell-agent.container`):

```ini
[Unit]
Description=OpenShell Standalone Agent Sandbox
After=network-online.target
Wants=network-online.target

[Container]
Image=quay.io/openshell/custom-sandbox:latest
Exec=--standalone --policy-rules=/etc/openshell/policy.rego --policy-data=/etc/openshell/policy-data.yaml --sandbox=agent-1 /usr/local/bin/agent-entrypoint
Volume=/etc/openshell:/etc/openshell:ro,z
Volume=/var/lib/agent:/workspace:rw,z
Volume=/var/log/openshell:/var/log:rw,z
Environment=ANTHROPIC_API_KEY_FILE=/run/secrets/anthropic-key
SecurityLabelType=container_runtime_t
AddCapability=NET_ADMIN

[Service]
Restart=on-failure
RestartSec=10
TimeoutStartSec=60
TimeoutStopSec=30

[Install]
WantedBy=multi-user.target
```

**Key quadlet features for standalone mode:**

- **Declarative configuration** - Entire sandbox defined in version-controlled file
- **systemd integration** - Standard `systemctl start/stop/status` commands work
- **Boot-time activation** - `WantedBy=multi-user.target` enables sandbox at boot
- **Dependency ordering** - `After=network-online.target` ensures network stack is ready
- **Restart policies** - `Restart=on-failure` handles transient errors
- **Resource limits** - Can add `MemoryMax=`, `CPUQuota=` for hard resource caps (systemd resource control)
- **Secret injection** - Use systemd `LoadCredential=` or bind-mount `/run/secrets/`
- **Log forwarding** - `journald` captures container stdout/stderr; OCSF logs in bind-mounted volume

**Alternative: Direct systemd unit** (without Podman):

For VM-based or bare-metal deployments, use a standard systemd service:

```ini
[Unit]
Description=OpenShell Standalone Agent (Docker)
After=docker.service
Requires=docker.service

[Service]
Type=simple
ExecStartPre=-/usr/bin/docker stop openshell-agent-1
ExecStartPre=-/usr/bin/docker rm openshell-agent-1
ExecStart=/usr/bin/docker run --rm --name openshell-agent-1 \
  --cap-add=NET_ADMIN \
  -v /etc/openshell:/etc/openshell:ro \
  -v /var/lib/agent:/workspace:rw \
  -v /var/log/openshell:/var/log:rw \
  -e ANTHROPIC_API_KEY_FILE=/run/secrets/anthropic-key \
  quay.io/openshell/custom-sandbox:latest \
  --standalone \
  --policy-rules=/etc/openshell/policy.rego \
  --policy-data=/etc/openshell/policy-data.yaml \
  --sandbox=agent-1 \
  /usr/local/bin/agent-entrypoint
ExecStop=/usr/bin/docker stop openshell-agent-1
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

**Benefits of systemd integration:**

1. **Certification-friendly** - systemd units are auditable, version-controlled, immutable at runtime
2. **Platform-native** - No custom orchestrator; uses standard Linux init system
3. **Resource enforcement** - Leverage systemd cgroups (MemoryMax, CPUQuota, TasksMax)
4. **Dependency management** - Explicit ordering (After=, Requires=, Wants=)
5. **Health monitoring** - systemd watchdog, restart policies, failure handling
6. **Logging integration** - journald captures all output, rotates logs, supports log forwarding

### Features Comparison

| Feature | Gateway mode | Standalone mode |
|---------|--------------|-----------------|
| Supervisor session (gRPC) | Required | Disabled |
| SSH server | Spawned | Disabled |
| Denial aggregator | Spawned, flushes every 10s | Disabled |
| Activity aggregator | Spawned, flushes every 60s | Disabled |
| Settings poll loop | Runs every 10s | Disabled |
| Provider credentials | From gateway | From env vars |
| Policy hot-reload | Supported | Disabled (static) |
| Policy proposals (RFC 0002) | Supported | Disabled |
| **Network enforcement** | ✓ | ✓ |
| **OPA policy engine** | ✓ | ✓ |
| **Filesystem isolation** | ✓ | ✓ |
| **Process restrictions** | ✓ | ✓ |
| **OCSF logging** | ✓ (pushed to gateway) | ✓ (local files only) |
| **systemd integration** | Via gateway deployment | Native (quadlets, units) |

### OCSF Logging in Standalone Mode

Standalone mode writes OCSF logs locally instead of pushing to gateway:

- **JSONL format**: Written to `/var/log/openshell-ocsf.log` (or path from `OPENSHELL_OCSF_LOG_PATH` env var)
- **No remote push**: Log aggregation is platform concern (use external log forwarder or journald)
- **Sandbox ID**: Uses `--sandbox` value if provided, otherwise generates `standalone-<uuid>` at boot
- **Same event types**: NetworkActivity, HttpActivity, ProcessActivity, etc. (per AGENTS.md OCSF guidelines)
- **journald integration**: Implicitly given by running as systemd unit; rotate OCSF files possible

### Resource Footprint Expectations

Expected resource usage (subject to validation):

| Metric | Gateway mode | Standalone mode | Expected reduction |
|--------|--------------|-----------------|-------------------|
| Background tasks | 5-7 | 1 (proxy only) | ~80% |
| Memory baseline | ~50-80 MB | ~20-30 MB | ~50-60% |
| Network connections | 1-2 (gateway) | 0 | 100% |
| Log volume | High (denials + activity + telemetry) | Low (enforcement only) | ~70% |

**Note:** These are estimates and should be validated with benchmarks during implementation.

## Implementation Plan

1. Add `--standalone` flag parsing and validation logic
2. Conditionally skip gateway-dependent spawns:
   - Supervisor session creation (`openshell-supervisor-process::supervisor_session::spawn`)
   - SSH server spawn (`openshell-supervisor-process::ssh`)
   - Aggregator spawns (`denial_aggregator`, `activity_aggregator`)
   - Settings poll loop
3. Handle missing/static sandbox_id in OCSF context
4. Write OCSF logs to local file path instead of gateway push

**Files to modify:**
- `crates/openshell-sandbox/src/main.rs` - Flag parsing, validation
- `crates/openshell-sandbox/src/lib.rs` - Conditional feature spawns
- `crates/openshell-supervisor-process/src/ssh.rs` - Conditional SSH spawn
- `crates/openshell-sandbox/src/activity_aggregator.rs` - Conditional spawn
- `crates/openshell-sandbox/src/denial_aggregator.rs` - Conditional spawn

**Testing:**
- Integration test: standalone mode with valid config
- Integration test: flag validation errors

## Risks and Mitigations

### Dual-Mode Maintenance Complexity

**Risk:** Maintaining gateway-integrated and standalone modes increases testing surface

**Mitigation:** Clear code separation with conditional blocks, dedicated integration tests for each mode

**Residual risk:** Medium (inherent complexity of dual-mode operation)

### Configuration Validation Gaps

**Risk:** Boot-time validation might miss runtime issues that gateway mode would catch

**Mitigation:** Strict schema validation at startup, comprehensive error messages, example configs

**Residual risk:** Medium (acceptable trade-off for QM validation workflows)

### Credential Management Complexity

**Risk:** Environment variable credentials less secure than gateway resolution

**Mitigation:** Document credential best practices, recommend platform-native secret injection (systemd `LoadCredential=`), warn against hardcoded credentials in policy files

**Residual risk:** Medium (inherent trade-off for air-gapped environments)

### systemd/Quadlet Version Compatibility

**Risk:** Podman quadlet support requires Podman 4.4+ and systemd 244+; older QM systems may lack support

**Mitigation:** Provide fallback examples using traditional `.service` units with `docker run` or `podman run`, document minimum versions

**Residual risk:** Low (quadlets are optional convenience; traditional units always work)

## Alternatives Considered

### 1. Minimal Gateway for Static Environments

Run lightweight local gateway alongside supervisor.

**Rejected:** Too heavy for QM; doesn't meet single-binary requirement; overkill for static environments.

### 2. Embedded Gateway in Supervisor

Embed gateway logic directly in supervisor binary.

**Rejected:** Massive binary size increase; duplicates code; violates separation of concerns (data plane vs control plane).

### 3. Policy-Only Mode Without Supervisor

Provide network policy runtime without full supervisor.

**Rejected:** Loses filesystem isolation, process restrictions, seccomp; not a complete security boundary.

### 4. Do Nothing

Document current file-based mode as-is.

**Rejected:** Current behavior wasteful and user-hostile for static environments; small investment yields large UX improvement.

### 5. Build Custom systemd Service Generator

Provide `openshell-sandbox generate-systemd` command to create `.service` or `.container` files.

**Rejected:** Overengineering for initial implementation. Users can write their own quadlets/units (examples provided). Can add generator later if demand is clear.

## Prior Art

- **containerd/CRI-O standalone modes** - Container runtimes with static config, no control plane
- **OPA standalone evaluation** - Policy loaded from files, no server required
- **Istio sidecar static mode** - xDS config from files instead of Pilot
- **systemd service hardening** - Declarative config with strict validation, deterministic lifecycle
- **Podman quadlets** - Declarative container-as-service model for systemd integration
- **podman generate systemd** - Generate systemd units from running containers (prior art for declarative deployment)

All demonstrate that static configuration with boot-time validation is proven for embedded/edge deployments.

## Open Questions

### Should standalone mode support hot-reload from filesystem?

**Recommendation:** Start without hot-reload. Policy is immutable for sandbox lifetime. If demand emerges, add `--watch-policy` flag as separate feature in Phase 4.

### Should standalone mode support provider inference routes configuration?

**Recommendation:** Defer to future work. Initial implementation denies all `inference.local` traffic unless routes are configured via environment variables (existing behavior). A dedicated `--inference-routes` file can be added later if needed.

### Should standalone mode support systemd `Type=notify` for ready signaling?

**Recommendation:** Defer to Phase 4. Initial implementation uses `Type=simple` (systemd considers service ready when `ExecStart` runs). If demand emerges, add `sd_notify(3)` call when supervisor is ready to enforce policy.

## Migration from Gateway Mode

Users migrating from gateway-integrated to standalone mode:

1. **Export current policy:**
   ```bash
   openshell-cli get-sandbox-config --sandbox-id=<id> --output-policy-data > policy-data.yaml
   # Use gateway's Rego or create custom policy.rego file
   ```

2. **Create systemd quadlet** (Podman):
   ```bash
   $ cat > /etc/containers/systemd/openshell-agent.container <<EOF
   [Container]
   Image=quay.io/openshell/custom-sandbox:latest
   Exec=--standalone --policy-rules=/etc/openshell/policy.rego --policy-data=/etc/openshell/policy-data.yaml /usr/local/bin/agent
   Volume=/etc/openshell:/etc/openshell:ro,z
   AddCapability=NET_ADMIN
   EOF
   $ systemctl daemon-reload
   $ systemctl enable --now openshell-agent.service
   ```

3. **Verify enforcement:**
   - Check OCSF logs: `journalctl -u openshell-agent -f` or `tail -f /var/log/openshell-ocsf.log`
   - Validate allowed connections succeed, denied connections fail
   - Confirm no gateway connection attempts in logs
   - Check systemd status: `systemctl status openshell-agent`
